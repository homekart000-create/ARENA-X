# Frontend Authentication Migration: Phase 1

The static frontend now uses the Step 19 cookie-session API for login, registration, logout, and session checks. The API base is configured only in `js/api.js` as `API_BASE_URL`. An empty value uses relative `api/...` requests, which is appropriate only when the static site and API are served from the same origin/path. Do not set a production URL until the backend has a real HTTPS deployment.

GitHub Pages currently serves only static files; it does not proxy `/api` requests. With the default empty base, authentication therefore reports the backend as unavailable on the current Pages deployment. When the API is deployed, set `API_BASE_URL` to its real HTTPS origin and add the exact GitHub Pages origin to the backend `CORS_ORIGINS`. The API must allow credentialed CORS and production cookies must retain the backend's `Secure`, `HttpOnly`, and `SameSite=None` settings. Browser third-party-cookie restrictions should be evaluated; a same-site API host is preferable where possible.

The browser never reads or stores the session cookie. Every page that loads auth checks `/api/auth/me`; protected pages wait for that result and redirect unauthenticated or expired sessions. Registration and login also verify the resulting session with `/api/auth/me`. The server controls session lifetime; the former local “remember me” behavior is not retained.

The current public responses from `/api/auth/me` and `/api/users/me` omit role and status. The frontend does not infer either from localStorage. Admin access therefore fails closed for every account, including backend admins, until a backend-authenticated role signal is provided through an approved contract. Do not re-enable the demo admin or infer admin from local data.

On load, the frontend removes password, password-hash, and session-token fields from records in `arena-x-users-v1`, and removes the legacy `arena-x-session-v1` entry. Other keys and competition/team/match/wallet data are left in place and are not migrated. A verified public user profile may be cached in the existing users key for local domain compatibility; role, status, demo flags, and credentials are not copied into that cache. If browser storage is unavailable, cleanup cannot be guaranteed and browser storage access should be restored before authentication is used.

The frontend remains plain HTML/CSS/JavaScript with no Node runtime or build step. The existing service worker and static GitHub Pages layout are unchanged.
